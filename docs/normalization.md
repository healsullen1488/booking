# Нормализация базы данных

СУБД: PostgreSQL 16. Схема: `db/01_tables.sql`, `db/02_constraints.sql`, `db/03_triggers.sql`.

## 0. Исходная «плоская» таблица

Первая версия хранила всё в одной таблице:

```
bookings_flat(
    id, title, start_at, end_at, people,
    room_name, room_floor, room_capacity, room_equipment,     -- "Проектор, ТВ"
    user_email, user_name, user_pass, user_role,              -- "MANAGER"
    status,                                                   -- "PENDING"
    history                                                   -- "создал; подтвердил; ..."
)
```

Аномалии:

| Аномалия | Пример |
| --- | --- |
| обновления | вместимость комнаты хранится в каждой её брони; поменяли в одной строке — данные разошлись |
| вставки | нельзя завести комнату, пока на неё нет ни одной брони |
| удаления | удалили последнюю бронь комнаты — потеряли саму комнату |
| неатомарность | «Проектор, ТВ» нельзя проиндексировать и отфильтровать |

## 1. Первая нормальная форма (1НФ)

Требования: значения атомарны, нет повторяющихся групп, у таблицы есть ключ.

* `room_equipment` в виде строки «Проектор, ТВ» → таблицы `equipment` и `room_equipment`
  (одна строка = одна пара «комната — оборудование»).
* `history` в виде текста → таблица `booking_history` (одна строка = одно действие).
* У каждой таблицы есть первичный ключ (`id` или составной).
* Время хранится как `timestamptz`, а не как строка «10:00-11:00».

## 2. Вторая нормальная форма (2НФ)

Требование: нет зависимости неключевых атрибутов от **части** составного ключа.

Составной ключ есть только у `room_equipment (room_id, equipment_id)` и
`status_moves (from_id, to_id)`. В них нет неключевых атрибутов, поэтому частичных
зависимостей быть не может. У остальных таблиц ключ из одного поля (`id`) — частичная
зависимость невозможна по определению.

## 3. Третья нормальная форма (3НФ)

Требование: нет транзитивных зависимостей «неключ → неключ».

В плоской таблице были цепочки:

* `booking.id → room_name → (room_floor, room_capacity)` — свойства комнаты → таблица `rooms`;
* `booking.id → user_email → (user_name, user_role)` — свойства пользователя → таблица `users`;
* `user_role` (текст) → справочник `roles`;
* `status` (текст) → справочник `statuses`; действие журнала → `actions`.

Теперь в `bookings` лежат только `room_id`, `user_id`, `status_id` и собственные
свойства брони (`title`, `people`, `start_at`, `end_at`, `created_at`).

## 4. Нормальная форма Бойса — Кодда (НФБК)

Требование: **каждый** детерминант функциональной зависимости является потенциальным ключом.

Функциональные зависимости по таблицам (детерминанты выделены):

| Таблица | Функциональные зависимости | Потенциальные ключи | НФБК |
| --- | --- | --- | --- |
| roles | **id** → name; **name** → id | id; name (`UNIQUE`) | да |
| statuses | **id** → name; **name** → id | id; name | да |
| actions | **id** → name; **name** → id | id; name | да |
| equipment | **id** → name; **name** → id | id; name | да |
| status_moves | (from_id, to_id) → ∅ | (from_id, to_id) | да |
| users | **id** → email, name, pass_hash, role_id, created_at; **lower(email)** → id | id; lower(email) (уникальный индекс) | да |
| rooms | **id** → name, floor, capacity, is_active; **name** → id | id; name (`UNIQUE`) | да |
| room_equipment | (room_id, equipment_id) → ∅ | (room_id, equipment_id) | да |
| bookings | **id** → room_id, user_id, status_id, title, people, start_at, end_at, created_at | id | да |
| booking_history | **id** → booking_id, user_id, action_id, status_id, start_at, end_at, at | id | да |

Замечания:

* В `bookings` нет зависимости `(room_id, start_at) → id`: у отменённых броней интервалы
  могут совпадать, поэтому такая пара не является ключом и не является детерминантом.
  Для активных броней пересечение запрещает `EXCLUDE` — это ограничение
  целостности, а не функциональная зависимость.
* В `booking_history` нет зависимости `(booking_id, at) → …`: две записи могут
  получить одинаковый `at` в одной транзакции (`now()` — время начала транзакции).

## 5. Четвёртая нормальная форма (4НФ)

Требование: нет нетривиальных **многозначных** зависимостей, не следующих из ключа.

Независимые многозначные факты вынесены в отдельные таблицы:

* оборудование комнаты — `room_equipment` (комната ↠ оборудование);
* допустимые переходы статусов — `status_moves` (статус ↠ следующие статусы);
* действия над бронью — `booking_history` (бронь ↠ действия).

Если бы оборудование и, например, список «разрешённых тарифов комнаты» хранились
в одной таблице, получилось бы декартово произведение — именно это и устранено.
Сейчас в каждой таблице-связке ровно две колонки, поэтому нарушений 4НФ нет.

## 6. Пятая нормальная форма (5НФ, проекционно-соединительная)

Требование: любая зависимость соединения следует из потенциальных ключей.

* Таблицы-связки `room_equipment` и `status_moves` бинарные: бинарное отношение без
  потерь не раскладывается на меньшие проекции.
* Трёхсторонних связей (например «комната + оборудование + пользователь») в предметной
  области нет: оборудование принадлежит комнате, а не брони.
* Остальные таблицы имеют единственный потенциальный ключ-«суррогат» (или пару ключей
  у справочников) и все атрибуты зависят от него целиком — зависимости соединения
  следуют из ключей.

## 7. Доменно-ключевая нормальная форма (ДКНФ)

Требование: все ограничения выражены через ограничения доменов и ключей.

| Ограничение предметной области | Как выражено |
| --- | --- |
| e-mail уникален без учёта регистра | уникальный индекс `lower(email)` (ключ) |
| вместимость > 0, этаж −5…100, участников > 0 | `CHECK` (домен) |
| длительность брони 15 мин … 4 ч, конец > начала | `CHECK bookings_len_ck`, `bookings_time_ck` (домен) |
| роль / статус / действие из справочника | внешние ключи |
| пересечения активных броней нет | `EXCLUDE USING gist` (ограничение на уровне таблицы) |
| участников не больше вместимости комнаты | **триггер** (ограничение между таблицами) |
| переход статуса только из `status_moves` | **триггер** |
| закрытую бронь нельзя менять | **триггер** |

Последние три правила связывают несколько таблиц или старое и новое значение строки,
`CHECK` их выразить не может — поэтому используются триггеры. Это осознанное и
единственное отступление от «чистой» ДКНФ.

## 8. Шестая нормальная форма (6НФ)

Применять не нужно: 6НФ полезна для темпоральных данных, где разные атрибуты меняются
независимо во времени. Здесь интервал брони (`start_at`, `end_at`) всегда меняется
вместе, а историю изменений хранит журнал `booking_history`. Разбивать `bookings` на
таблицы по одному атрибуту незачем.

## 9. Осознанная денормализация

| Что | Зачем | Как держится согласованность |
| --- | --- | --- |
| `bookings.status_id` дублирует последнюю запись `booking_history` | быстрый фильтр по статусу и ограничение `EXCLUDE ... WHERE status_id IN (1, 2)` без выборки из журнала | смена статуса и запись в журнал идут в одной транзакции (`BookingService._change`); запрос 11.4 в `db/05_queries.sql` проверяет расхождение |
| `booking_history.start_at`, `end_at`, `status_id` — снимок брони | аудит должен показывать, что было **на момент** действия | это не зависимость от `bookings`, а факт строки журнала (зависит от `id` записи); триггер `t_history_ro` запрещает менять журнал |

Для 3НФ это не нарушение: поля снимка зависят от ключа записи журнала, а не от брони.

## 10. Итог

Схема из 10 таблиц находится в 1НФ, 2НФ, 3НФ, НФБК, 4НФ и 5НФ; ограничения предметной
области выражены ключами, доменами (`CHECK`), внешними ключами, `EXCLUDE` и триггерами.
